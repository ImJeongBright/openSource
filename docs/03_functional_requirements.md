# 기능 요구사항 명세서 (Functional Requirements Specification)

**프로젝트명**: OpenSQL 기반 AI 문서 검색 및 버전 관리 시스템  
**문서 버전**: v1.0  
**작성일**: 2026-08-05

---

## 1. 요구사항 분류 체계

요구사항 ID 형식: `FR-[영역]-[번호]`

| 영역 코드 | 설명 |
|---------|------|
| DOC | 문서 관리 |
| PIPE | 처리 파이프라인 |
| STORE | 데이터 저장 |
| SEARCH | 검색 |
| MCP | MCP 인터페이스 |
| RECOVERY | 장애 복구 |

## 2. 문서 관리 요구사항 (FR-DOC)

### FR-DOC-01: 문서 업로드 지원 형식
- 시스템은 PDF, TXT, Markdown(.md, .markdown) 형식의 파일 업로드를 지원해야 한다.
- 지원하지 않는 형식의 파일은 명확한 오류 메시지와 함께 거부해야 한다.

### FR-DOC-02: 파일 크기 제한
- 단일 파일의 최대 크기는 100MB로 제한한다.
- 크기 초과 시 업로드 요청을 거부하고 오류를 반환해야 한다.

### FR-DOC-03: 문서 메타데이터 관리
- 문서 업로드 시 다음 메타데이터를 수집하고 저장해야 한다:
  - 문서 제목 (필수)
  - 파일 형식
  - 파일 크기
  - 업로드 일시
  - 업로더 식별자 (선택)
  - 카테고리/태그 (선택)

### FR-DOC-04: 문서 버전 관리
- 동일 문서의 수정본 업로드 시 새로운 버전 번호를 자동 부여해야 한다. (정수 순번: 1, 2, 3, ...)
- 각 버전은 독립적인 청크 및 임베딩 데이터를 보유해야 한다.
- 버전 삭제는 지원하지 않는다. (ARCHIVED 상태로 보존)

### FR-DOC-05: 문서 삭제
- 문서 삭제 시 해당 문서의 모든 버전, 청크, 임베딩 벡터를 물리적으로 삭제해야 한다.
- 삭제 이벤트는 변경 로그에 기록되어야 한다.

### FR-DOC-06: 문서 목록 조회
- ACTIVE 버전이 존재하는 문서 목록을 반환해야 한다.
- 카테고리, 날짜 범위, 처리 상태 기준 필터링을 지원해야 한다.
- 결과에는 문서명, 최신 버전 번호, 마지막 업데이트 일시, 총 청크 수가 포함되어야 한다.

### FR-DOC-07: 버전 이력 조회
- 특정 문서의 모든 버전 이력을 조회할 수 있어야 한다.
- 버전별 상태(PENDING/PROCESSING/ACTIVE/ARCHIVED/FAILED), 생성 일시, 청크 수, 처리 완료 시간이 포함되어야 한다.

## 3. 처리 파이프라인 요구사항 (FR-PIPE)

### FR-PIPE-01: 비동기 처리
- 문서 업로드 후 텍스트 추출, 청킹, 임베딩은 비동기로 수행되어야 한다.
- 업로드 요청은 즉시 접수 확인을 반환하고, 처리는 백그라운드에서 진행되어야 한다.

### FR-PIPE-02: 텍스트 추출
- **PDF**: 페이지 번호와 함께 텍스트를 추출해야 한다. 이미지 전용 페이지는 건너뛴다.
- **TXT**: 원문 텍스트를 그대로 사용한다.
- **Markdown**: 마크다운 문법을 파싱하여 섹션 제목(heading) 정보를 보존한다.

### FR-PIPE-03: 청킹 (Chunking)
- 텍스트를 설정 가능한 크기(chunk_size, 기본값 512 토큰)로 분할해야 한다.
- 청크 간 중복(overlap, 기본값 50 토큰)을 지원하여 문맥 단절을 최소화해야 한다.
- 각 청크에는 다음 정보가 함께 저장되어야 한다:
  - 청크 순번
  - 원본 페이지 번호 (PDF의 경우)
  - 섹션 제목 (Markdown의 경우)
  - 청킹 파라미터 (chunk_size, overlap) — 재현성을 위해 버전 메타데이터에 저장
  
### FR-PIPE-04: 임베딩 생성
- 각 청크 텍스트를 자체 관리 Ollama의 오픈웨이트 임베딩 모델에 전달하여 벡터를 생성해야 한다.
- 사용된 임베딩 모델명과 버전을 청크 메타데이터에 함께 저장해야 한다.
- 임베딩 벡터 차원수는 모델과 DB 스키마가 일치해야 한다. (Qwen3 기본값: 1024차원)

### FR-PIPE-05: 처리 상태 추적
- 각 처리 단계(추출/청킹/임베딩/전환)의 시작 및 완료 시각을 기록해야 한다.
- 청크 단위로 임베딩 완료 여부를 추적할 수 있어야 한다.

## 4. 데이터 저장 요구사항 (FR-STORE)

### FR-STORE-01: 통합 저장소
- 문서 메타데이터, 버전 이력, 청크 텍스트, 임베딩 벡터, 변경 로그 모두 OpenSQL 단일 DB에 저장해야 한다.

### FR-STORE-02: Atomic 버전 전환
- 새 버전의 모든 청크 임베딩이 완료된 후에만 해당 버전을 ACTIVE로 전환해야 한다.
- 이전 ACTIVE 버전을 ARCHIVED로 변경하고, 새 버전을 ACTIVE로 변경하는 작업은 단일 트랜잭션으로 수행되어야 한다.
- 전환 실패 시 기존 ACTIVE 버전이 그대로 유지되어야 한다.

### FR-STORE-03: 변경 로그 기록
- 다음 이벤트는 반드시 변경 로그에 기록되어야 한다:
  - UPLOAD (새 문서 등록)
  - UPDATE (새 버전 등록)
  - DELETE (문서 삭제)
  - EMBED_START / EMBED_COMPLETE / EMBED_FAIL (임베딩 처리 진행)
  - VERSION_SWITCH (버전 전환)
- 변경 로그에는 이벤트 유형, 대상 문서 ID, 버전 번호, 타임스탬프, 상태, 실패 사유가 포함되어야 한다.

### FR-STORE-04: 임베딩 모델 버전 추적
- 각 청크의 임베딩 생성에 사용된 모델명과 버전을 별도 컬럼에 저장해야 한다.
- 임베딩 모델 교체 시 기존 벡터와 새 벡터를 구분할 수 있어야 한다.

## 5. 검색 요구사항 (FR-SEARCH)

### FR-SEARCH-01: 의미 검색 (Semantic Search)
- 자연어 질의를 임베딩 벡터로 변환한 후, pgvector의 코사인 유사도를 이용해 관련 청크를 검색해야 한다.
- 검색 대상은 ACTIVE 버전의 청크에 한정되어야 한다.

### FR-SEARCH-02: 검색 결과 구성
- 검색 결과 각 항목에는 다음 정보가 포함되어야 한다:
  - 청크 텍스트 (근거 문단)
  - 문서 제목
  - 문서 버전 번호
  - 페이지 번호 (해당하는 경우)
  - 섹션 제목 (해당하는 경우)
  - 코사인 유사도 점수

### FR-SEARCH-03: 검색 필터링
- 다음 조건으로 검색 범위를 좁힐 수 있어야 한다:
  - 특정 문서 ID 또는 제목
  - 카테고리/태그
  - 날짜 범위 (문서 생성일 기준)
  - 최소 유사도 임계값

### FR-SEARCH-04: 결과 수 제어
- 검색 시 반환할 결과 수(top_k)를 지정할 수 있어야 한다. (기본값: 5, 최대: 50)

### FR-SEARCH-05: 인덱스 재구축
- 관리자가 명령으로 pgvector 인덱스를 재구축할 수 있어야 한다.
- 재구축 시 DB에 저장된 임베딩 벡터 데이터를 기준으로 수행해야 한다.

## 6. MCP 인터페이스 요구사항 (FR-MCP)

### FR-MCP-01: search_documents 도구
- **설명**: 자연어 질의로 관련 문서 청크를 검색한다.
- **입력 파라미터**:
  - `query` (string, 필수): 자연어 검색 질의
  - `top_k` (integer, 선택, 기본값 5): 반환 결과 수
  - `filters` (object, 선택): 카테고리, 날짜 범위 등 필터 조건
- **출력**: 청크 텍스트, 문서명, 버전, 페이지, 섹션, 유사도 점수 목록

### FR-MCP-02: get_document 도구
- **설명**: 특정 문서의 메타데이터 및 버전 정보를 조회한다.
- **입력 파라미터**:
  - `document_id` (string, 필수)
  - `version` (integer, 선택, 기본값: 최신 ACTIVE)
- **출력**: 문서 메타데이터, 버전 정보, 청크 수

### FR-MCP-03: list_documents 도구
- **설명**: 시스템에 저장된 ACTIVE 문서 목록을 반환한다.
- **입력 파라미터**:
  - `filters` (object, 선택)
  - `page` / `page_size` (integer, 선택): 페이지네이션
- **출력**: 문서 목록 (제목, 버전, 마지막 업데이트 일시)

### FR-MCP-04: get_chunk 도구
- **설명**: 청크 ID로 청크 원문 및 근거 위치를 조회한다.
- **입력 파라미터**:
  - `chunk_id` (string, 필수)
- **출력**: 청크 텍스트, 문서명, 버전, 페이지, 섹션 제목

## 7. 장애 복구 요구사항 (FR-RECOVERY)

### FR-RECOVERY-01: 변경 로그 기반 재시도
- Worker 재시작 시 변경 로그의 PENDING/FAILED 항목을 자동으로 감지하고 재처리해야 한다.
- 재처리 시 이미 완료된 청크의 임베딩은 재생성하지 않아야 한다. (멱등성)

### FR-RECOVERY-02: 재시도 횟수 제한
- 단일 작업 항목의 최대 재시도 횟수는 설정 가능해야 한다. (기본값: 3회)
- 최대 횟수 초과 시 해당 항목을 DEAD_LETTER 상태로 전환하고 알림을 발송해야 한다.

### FR-RECOVERY-03: 동시 처리 충돌 방지
- 동일한 변경 로그 항목을 여러 Worker가 동시에 처리하지 않도록 락(Locking) 메커니즘이 있어야 한다.

### FR-RECOVERY-04: DB 노드 장애 대응
- OpenSQL의 Patroni HA 구조를 통해 Primary 노드 장애 시 자동 Failover가 수행되어야 한다.
- Failover 후 미처리 변경 로그 항목은 Worker 재시작 시 자동으로 재처리되어야 한다.

# Phase 5: 임베딩 API 클라이언트 및 업로드 API 구현 상세

## 1. 개요
본 단계에서는 외부 사용자가 문서를 시스템에 전달할 수 있는 API를 노출하고, 내부적으로 파이프라인에서 생성된 텍스트 청크를 벡터로 변환하기 위해 외부 AI 모델(임베딩 API)과 통신하는 클라이언트 모듈을 구축합니다.

## 2. 세부 구현 목표

### 2.1. 업로드 및 상태 확인 API (`src/api/routes.py`)

#### 문서 업로드 엔드포인트 구현 (FastAPI)
- **방식**: `UploadFile`을 활용해 파일을 multipart/form-data 형식으로 수신합니다.
- **해시 계산**: 수신한 파일을 메모리 또는 임시 디렉토리에 저장하면서 내용의 SHA-256 해시를 즉시 계산하여 동일한 파일이 중복으로 업로드되는 것을 방지합니다.

#### 원자적 트랜잭션 기록 (Atomic INSERT)
- 파일이 새롭게 검증되면 단일 트랜잭션 내에서 다음 테이블들에 일괄 INSERT 작업을 수행합니다:
  1. `documents`: 문서의 기본 정보와 파일 해시 기록.
  2. `document_versions`: 문서의 신규 버전을 생성하고 처리 상태 초기화.
  3. `change_log`: 파이프라인 워커가 픽업할 수 있도록 상태를 `PENDING`으로 기록.
- 이 과정이 모두 성공해야만 파일이 시스템에 접수된 것으로 처리됩니다.

#### 진행률 확인 엔드포인트 구현
- 클라이언트(또는 대시보드 UI)가 파일 업로드 후 진행 상태를 확인할 수 있도록 API를 제공합니다.
- 사전에 설계된 `processing_status` 뷰 등을 조회하여, 해당 버전의 전체 청크 수 대비 임베딩 완료된 청크 수를 바탕으로 진행률 퍼센티지 (`embedded_chunks / total_chunks * 100`)를 산출해 반환합니다.

### 2.2. 임베딩 클라이언트 모듈 (`src/embedding/client.py`)

#### 배치 처리 최적화 (Batching)
- **문제점**: 수천 개의 청크를 API 서버로 하나씩 보내면 Rate Limit 에러나 네트워크 오버헤드가 발생합니다.
- **해결책**: 텍스트 청크 리스트를 100개 단위 등 정해진 배치(Batch) 사이즈로 묶어서 OpenAI API 등의 임베딩 모델에 한 번에 전송합니다. 배치 사이즈는 설정(Configuration)에서 주입받습니다.

#### 안정성 및 재시도 확보
- **라이브러리 도입**: `tenacity`와 같은 라이브러리를 사용해 API 호출 실패 시 안정적인 Retry 로직(예: 429 Too Many Requests 에러 처리)을 적용합니다.
- **오류 격리**: 배치를 처리하다가 오류가 난 경우, 해당 배치만 실패로 처리하고 파이프라인 워커에게 에러를 전파하여 후속 처리를 위임합니다.

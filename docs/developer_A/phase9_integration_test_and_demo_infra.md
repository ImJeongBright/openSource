# Phase 9: 통합 테스트 및 데모 시나리오 준비 상세 (인프라 중심 - Developer A)

## 1. 개요
본 단계는 시스템의 견고함, 가용성 및 장애 복구 능력을 인프라 관점에서 증명하기 위한 단계입니다. 데모 전에 단일 노드 개발 환경과 Patroni HA 환경을 구분하고, 실제로 구성되지 않은 HA 기능을 동작한 것처럼 발표하지 않습니다.

## 2. 세부 테스트 및 데모 기획

### 2.1. 하드코어 테스트 시나리오 구성 (복원력 시연)

#### 워커 프로세스 강제 종료 (Chaos Testing)
- **상황 연출**: 파이프라인 워커가 대용량 문서를 처리하며 한창 임베딩 API를 호출하고 있는 도중, `kill -9` 명령어로 해당 프로세스를 강제 종료시킵니다.
- **기대 결과 및 데모 포인트**: 
  - 멈춘 작업은 일시적으로 `PROCESSING` 상태로 남고 lease timeout 후 `PENDING`으로 복구됩니다.
  - 데모 화면에서 스위퍼(Sweeper) 로직이 주기적으로 동작하여 해당 작업을 찾아내 다시 `PENDING`으로 복구하는 모습을 보여줍니다.
  - 다른 워커(혹은 재시작된 워커)가 복구된 작업을 가져와, 이미 처리된 청크는 건너뛰고(멱등성) 남은 청크부터 이어서 작업을 완수하는 것을 시연합니다.

#### 데이터베이스 장애 유발 및 Failover 시연 (Patroni HA 환경에서만)
- **상황 연출**: OpenSQL 클러스터(Patroni 기반 HA 구성)가 실제로 준비된 경우에만 활성 상태인 Primary 인스턴스를 인위적으로 중지(Stop) 시킵니다.
- **기대 결과 및 데모 포인트**:
  - 즉각적으로 클러스터 내 다른 Replica가 Primary로 승격(Failover)되는 과정을 모니터링 툴(또는 터미널 로그)로 보여줍니다.
  - 시스템과 워커 애플리케이션이 연결 끊김을 감지한 뒤, OpenProxy 또는 검증된 Primary endpoint를 통해 새로운 Primary로 재접속하여 작업을 재개하는 모습을 시연합니다.

> 단일 노드 환경에서는 Patroni Failover를 시연하지 않고, DB 연결 오류 후 트랜잭션 롤백과 Worker 재처리만 검증합니다. `kill -9`와 Primary 중지는 격리된 데모 환경에서만 수행합니다.

### 2.2. 퍼포먼스 벤치마크 지표 시각화
- **메트릭 수집**: 각 단계별 병목 현상을 분석하기 위해 문서 추출, 청킹, 배치 저장, 인덱싱에 걸리는 소요 시간 데이터를 수집합니다.
- **출력 구성**: 우선 구조화 로그로 단계별 소요 시간과 처리량을 남기고, 별도 대시보드가 실제 구현된 경우에만 그래픽을 사용합니다. 측정하지 않은 수치를 발표 자료에 기입하지 않습니다.
- **어필 포인트**: 심사위원에게 시스템의 안정성뿐만 아니라 대용량 데이터 처리에 대한 깊은 기술적 고민과 엔지니어링 역량을 강조합니다.

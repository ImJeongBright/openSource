# Phase 7: Atomic 버전 전환 및 파이프라인 통합 상세 (Developer A)

## 1. 개요
본 단계에서는 개별적으로 개발된 텍스트 추출, 청킹, 임베딩 모듈들을 하나의 완전한 파이프라인으로 연결합니다. 파이프라인의 최종 단계에서 모든 데이터가 올바르게 적재되었음을 검증하고, 새 문서 버전을 `ACTIVE` 상태로 원자적(Atomic)으로 전환하여 검색 엔진에 일관성 있는 데이터만 노출되도록 보장합니다. 배치 저장은 Developer B의 책임이고, A는 저장 완료 조건·전환·재시도 경계를 책임집니다.

## 2. 세부 구현 목표

### 2.1. 저장 함수 연동 및 검증 (`src/pipeline/versioner.py`)
- **종료 조건 확인**: 워커 파이프라인의 마지막 단계에서 `document_versions`의 카운터만 신뢰하지 말고, 해당 버전의 `chunks`와 `embeddings`를 DB에서 다시 집계합니다. `total_chunks = embedded_chunks`이고 미임베딩 청크 및 누락 벡터가 없을 때만 전환합니다.
- **원자적 상태 전환 (`activate_version`)**:
  - 검증을 통과하면, OpenSQL 저장 함수(Stored Procedure/Function)인 `activate_version(version_id)`을 호출합니다.
  - 이 함수는 단일 데이터베이스 트랜잭션 내에서 다음을 수행해야 합니다. 같은 문서에 대한 동시 전환을 막기 위해 대상 `documents` 행을 잠그는 것도 함수의 책임입니다:
    1. 해당 문서(`document_id`)에 이미 존재하는 `ACTIVE` 버전이 있다면 이를 찾아 상태를 `ARCHIVED`로 변경합니다.
    2. 새롭게 처리가 완료된 문서 버전(`version_id`)의 상태를 `ACTIVE`로 설정합니다.
  - 이를 통해 검색 시스템은 어느 순간에도 절반만 적재된 문서를 노출하지 않게 되며 완벽한 정합성을 유지합니다.

### 2.2. 멱등성(Idempotency) 검증 체계 구축
- **파이프라인 재실행 보장**: 작업이 파이프라인 중간(예: 임베딩 처리 중 네트워크 오류)에 실패하여 스위퍼를 통해 다시 처리되더라도, 데이터가 중복으로 쌓이지 않아야 합니다.
- **중복 작업 건너뛰기**:
  - `is_embedded = TRUE`만으로 판단하지 말고 `embeddings`의 `chunk_id` 존재 여부도 확인합니다. 두 값이 어긋난 경우를 복구할 수 있어야 합니다.
  - 임베딩 INSERT와 `chunks.is_embedded` 갱신 및 `embedded_chunks` 증가를 하나의 배치 트랜잭션으로 처리합니다. 재실행 시에는 `ON CONFLICT (chunk_id) DO NOTHING` 또는 사전 조회로 실제 신규 저장 건수만 카운터에 반영합니다.
  - 미처리된 청크만 선별하여 다시 임베딩 과정을 거치도록 처리 파이프라인에 분기 로직을 구성합니다.

## 3. 테스트 고려사항
- 에러 상황을 의도적으로 발생시킨 후 재시도 시, 데이터 중복이나 누락 없이 정확히 `total_chunks`와 일치하게 완료되는지 통합 테스트로 증명합니다.
- `activate_version()` 호출 시 두 개 이상의 버전이 동시에 `ACTIVE` 상태가 되는 동시성 버그(Race Condition)가 없는지 같은 문서의 다중 프로세스 환경에서 테스트합니다. 부분 유니크 인덱스가 오류를 내는지만 확인하지 말고, 항상 기존 ACTIVE가 보존되거나 새 버전 하나만 ACTIVE가 되는 최종 상태를 검증합니다.

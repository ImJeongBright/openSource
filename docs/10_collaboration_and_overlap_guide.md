# 협업 및 교차점(Overlap) 관리 가이드

본 문서는 개발자 A와 개발자 B가 각자 담당한 Phase를 구현하는 과정에서 발생할 수 있는 **업무 중첩(Overlap)**, **데이터 핸드오프(Hand-off)**, 그리고 **잠재적 충돌 요소**를 사전에 정의하고 조율하기 위한 확정 문서입니다.

## 1. Phase 4 (A) ↔ Phase 5 (B) : 청크 데이터 핸드오프
**[교차점]** 개발자 A가 텍스트를 추출하고 청킹한 결과물(`src/pipeline/chunker.py`)을 개발자 B가 만든 임베딩 API 클라이언트(`src/embedding/client.py`)로 전달해야 합니다.

* **협업 규칙 및 충돌 방지**:
  * **인터페이스 확정**: 두 개발자는 `src/models.py`에 정의될 `ChunkData` Pydantic 모델의 구조(텍스트 내용, 페이지 번호, 섹션 제목 등)를 완벽하게 일치시켜야 합니다.
  * **독립적 테스트 보장**: 개발자 B는 A의 청킹 로직이 완성되기 전이라도, 임의의 더미 문자열 배열(Mock Data)을 사용해 임베딩 클라이언트 배칭 로직을 먼저 개발하고 테스트할 수 있어야 합니다.

## 2. Phase 5 (B) ↔ Phase 6 (A) : 워커 큐(Queue) 통신
**[교차점]** 개발자 B의 업로드 API는 파일 수신 후 `change_log` 테이블에 `PENDING` 상태로 기록(Insert)합니다. 개발자 A의 Worker 데몬은 이 테이블을 감시(Select)하여 작업을 픽업합니다.

* **협업 규칙 및 충돌 방지**:
  * **상태값 Enum 동기화**: `PENDING`, `PROCESSING`, `FAILED` 등의 상태 문자열에 오타나 불일치가 발생하지 않도록 `sql/02_types.sql`에 정의된 DB ENUM 타입을 코드 단독으로 수정하지 않고 반드시 합의하에 변경합니다.
  * **트랜잭션 가시성**: 개발자 B의 API 트랜잭션이 완벽히 `COMMIT`된 이후에만 개발자 A의 워커가 해당 데이터를 읽어갈 수 있으므로, B는 API 로직에서 트랜잭션 관리를 철저히 해야 합니다.
  * **원본 파일 계약**: B는 원본을 `UPLOAD_DIR/<version_id>.<확장자>`에 저장하고, A는 `version_id`로 해당 경로를 계산합니다. 사용자 파일명을 경로에 직접 사용하지 않습니다.

## 3. Phase 7 (A & B) : 파이프라인 최종 통합 (가장 큰 Overlap)
**[교차점]** Phase 7은 두 개발자가 동일한 파이프라인의 끝단을 다룹니다. 개발자 B는 임베딩 벡터를 DB에 벌크 저장(Batch Insert)하고 청크의 상태를 업데이트하며, 개발자 A는 모든 청크가 저장되었는지 검증한 뒤 문서 버전을 `ACTIVE`로 전환합니다.

* **협업 규칙 및 충돌 방지**:
  * **실행 순서 동기화**: 워커 데몬 내에서 코드가 실행될 때, 반드시 **B의 벡터 배치 저장 로직(COMMIT)이 완전히 끝난 직후에 A의 검증 및 버전 전환 로직(`activate_version`)이 호출**되도록 워커 루프의 순서를 확정해야 합니다.
  * **멱등성 처리 분담**: 재시도 상황 발생 시, 개발자 A의 로직이 이미 임베딩된 청크를 걸러내어 개발자 B의 함수로 전달해 주어야 불필요한 API 비용 발생을 막을 수 있습니다.

## 4. Phase 8 (B) : 벡터 검색 및 버전 상태 의존성
**[교차점]** 개발자 B가 개발하는 벡터 검색 쿼리는 반드시 '현재 서비스 중인' 문서에서만 검색을 수행해야 합니다. 이 '서비스 중'이라는 상태(`ACTIVE`)는 개발자 A가 만든 함수에 의해 결정됩니다.

* **협업 규칙 및 충돌 방지**:
  * **검색 조건 강제**: 개발자 B는 SQL 작성 시 `JOIN document_versions WHERE status = 'ACTIVE'` 조건을 반드시 포함하여, 파이프라인에서 실패했거나 과거 버전인 문서가 검색되지 않도록 보장해야 합니다.
  * **원자성 신뢰**: B는 A가 구현한 `activate_version()`이 짧은 순간이라도 두 개의 버전을 활성화하는 버그가 없다고 신뢰하고 UI/검색 결과를 구성합니다. (A의 철저한 테스트 필요)

## 5. Phase 9 (A & B) : 시나리오 데모 통합
**[교차점]** 시연 시 개발자 A는 데이터베이스를 강제로 끄거나 워커를 죽이는 하드코어 인프라 장애 시연을 준비하고, 개발자 B는 Claude를 통한 AI 자율 검색을 시연합니다.

* **협업 규칙 및 충돌 방지**:
  * **통합 시연 환경**: 로컬이나 단일 서버에 전체 스택(DB HA 클러스터, 워커 컨테이너, API 서버, MCP 서버)을 띄우는 `docker-compose` 또는 스크립트를 공동으로 작성합니다.
  * **시나리오 연계**: A가 장애 복구 시연을 통해 파이프라인이 멈췄다가 다시 돌아가 문서를 `ACTIVE`로 무사히 전환하면, 즉시 이어서 B가 Claude를 띄워 방금 올라온 문서를 검색하는 매끄러운 릴레이 데모를 연습합니다.

## 1. 프로젝트 배경

### 1.1 문제 인식

기업 내 문서 관리 환경에서는 PDF, TXT, Markdown 등 다양한 형식의 문서가 지속적으로 업로드되고 수정된다. 이 과정에서 다음과 같은 문제가 반복적으로 발생한다.

| 문제 | 설명 |
|------|------|
| **버전 불일치** | 문서가 수정되었으나 검색 인덱스에는 이전 버전의 임베딩이 남아 있어 오래된 내용이 검색 결과로 노출됨 |
| **임베딩 동기화 실패** | Worker 또는 DB 노드 장애 시 임베딩 처리가 중간에 중단되어 일부 청크만 반영된 불완전한 상태가 유지됨 |
| **벡터 DB 이원화** | 문서 메타데이터는 RDBMS, 벡터는 별도 벡터 DB에 저장되어 운영 복잡성과 데이터 정합성 관리 부담이 가중됨 |
| **추적성 부재** | AI가 생성한 답변이 어떤 문서의 어느 버전, 어느 페이지를 근거로 하는지 확인이 불가능함 |

### 1.2 기회

- Tmax OpenSQL에 내장된 **pgvector 확장**을 활용하면 벡터 검색과 관계형 데이터를 단일 DB에서 통합 관리할 수 있다.
- OpenSQL의 **고가용성(Patroni + etcd)** 구조는 장애 상황에서도 데이터 유실 없는 운영을 가능하게 한다.
- **MCP(Model Context Protocol)** 인터페이스를 표준화하면 Claude, GPT 등 다양한 AI 도구가 동일한 검색 API를 재사용할 수 있다.

## 2. 프로젝트 목표

### 2.1 핵심 목표

1. **통합 저장소 구축**: 문서 원본 정보, 버전 이력, 청크, 임베딩 벡터, 처리 로그를 OpenSQL 단일 DB에서 관리한다.
2. **Atomic 버전 전환**: 새 버전의 임베딩이 100% 완료되기 전까지 기존 버전을 검색 대상으로 유지한다.
3. **장애 복구 보장**: 변경 로그(change_log)를 기준으로 실패한 작업을 재시도하며, 멱등성(Idempotency)을 보장한다.
4. **추적 가능한 검색**: 검색 결과마다 문서명, 버전, 페이지, 근거 문단을 제공한다.
5. **AI 도구 연동**: MCP 표준 인터페이스를 통해 외부 AI 서비스가 검색 기능을 재사용할 수 있게 한다.

### 2.2 목표 외 범위 (Out of Scope)

- 문서 편집 기능 (외부 편집 도구에서 업로드만 지원)
- 사용자 인증/권한 관리 시스템 (별도 IAM 연동 가정)
- LLM 직접 통합 (MCP 인터페이스까지만 제공, LLM 선택은 사용처에서 결정)

## 4. 프로젝트 범위

### 4.1 포함 범위

```
[문서 업로드]
  ├── PDF / TXT / Markdown 파일 수신
  ├── 텍스트 추출 (PDF 파싱, 구조 보존)
  ├── 청킹 (chunk_size, overlap 파라미터화)
  └── 임베딩 생성 (외부 임베딩 API 연동)

[데이터 저장 - OpenSQL]
  ├── 문서 메타데이터 및 버전 이력
  ├── 청크 데이터 (텍스트 + 위치 정보)
  ├── 임베딩 벡터 (pgvector)
  └── 처리 상태 및 변경 로그

[검색 서비스]
  ├── pgvector 기반 의미 검색
  ├── 필터링 (버전, 문서 유형, 날짜 등)
  └── 결과 메타데이터 포함 (문서명, 버전, 페이지, 근거 문단)

[MCP 인터페이스]
  ├── search_documents 도구
  ├── get_document_version 도구
  └── list_documents 도구

[운영 기능]
  ├── 변경 로그 기반 작업 재시도
  ├── 임베딩 인덱스 재구축
  └── 버전 전환 Atomic 처리
```

### 4.2 기술 스택

| 영역 | 기술 |
|------|------|
| 데이터베이스 | Tmax OpenSQL 3.17.8.7 (PostgreSQL 17.8 기반) |
| 벡터 검색 | pgvector 0.8.1 |
| 고가용성 | Patroni 4.0.5 + etcd 3.6.5 |
| 임베딩 모델 | 외부 API (OpenAI text-embedding-3-small 등, 교체 가능) |
| 파이프라인 | Python 3.x + 비동기 Worker |
| MCP 서버 | Python MCP SDK |
| 문서 파싱 | PyMuPDF (PDF), mistune (Markdown) |

## 5. 성공 기준 (Success Criteria)

| 지표 | 목표 |
|------|------|
| 버전 불일치율 | 0% (전환 완료 전 기존 버전 유지 보장) |
| 장애 후 데이터 복구율 | 100% (변경 로그 기반 재처리) |
| 검색 결과 추적성 | 100% (모든 결과에 문서명·버전·페이지·근거 포함) |
| 의미 검색 지연시간 (p95) | ≤ 500ms |
| MCP 도구 응답 성공률 | ≥ 99.5% |

---

## 6. 제약 사항 및 전제 조건

- OpenSQL 클러스터는 사전에 설치 및 운영 중이어야 한다.
- 임베딩 생성을 위한 외부 API 키 및 네트워크 접근이 사전에 구성되어 있어야 한다.
- 임베딩 모델 교체 시 기존 벡터 전체 재생성이 필요하다. (배치 재처리 전략 수립 필요)
- 단일 문서의 최대 크기는 100MB 이내로 가정한다.
